## 3. F-10 이 차단을 실제로 푸는가 — 아니오

세 가지가 겹친다.

**① 설계가 스스로 범위를 한정한다.** 설계 문서 §6.5:

> F-10 이 달성하는 것은 **"로컬 push 경로까지의 강제"** 이지 "게이트 없이는 코드가 들어올 수 없음"이 아니다. 리뷰어가 이를 불충분하다고 판정할 수 있으며, **그것은 정당한 판정이다.**

**② 배선이 클론별 수동이다.** 훅은 `core.hooksPath` 로 가리켜야 작동하는데 이 설정은 클론 로컬이다. **현재 클론에서 미설정**이며, 병합만으로는 어느 클론에도 배선이 생기지 않는다.

**③ 배선 도구가 구현돼 있지 않다.** 설계 §5.1 이 `scripts/ops/install_hooks.py` 를 요구하지만 브랜치에 **존재하지 않는다**. 추적되는 것은 `.githooks/pre-push` 하나뿐이다.

**④ 설계 문서 자체가 검토 대기다.** 상태: "사용자 승인 2026-08-13. 작성된 스펙 검토 대기." 미검토 설계를 병합에 동반시키는 것은 차단을 푸는 게 아니라 옮기는 것이다.

즉 **B 를 병합해도 F-10 이 노리는 강제는 성립하지 않는다.** 규모만 2.2배가 된다.

## 4. 결정 근거

### A 를 고르는 이유

- **병합 대상이 작을수록 리뷰가 가능하다.** A 는 코드 10파일이고 그중 4개가 테스트다. B 는 여기에 미검토 설계 2,123행을 얹는다.
- **F-10 은 A 의 내용에 대한 지적이 아니다.** 안전망 수정의 정확성이 아니라 **저장소 전반의 게이트 강제**를 요구한 것이다. 성격이 다른 요구를 같은 PR 에 묶으면 둘 다 판단이 어려워진다.
- **A1a 배치처가 A 로 충분하다.** 탐지 전용이 의존하는 플래그 기반은 A 에 이미 있다. B 는 필요 없다.
- **P0-1 이 열려 있는 시간을 줄인다.** 안전망 무발화는 현재 운영 사실이고, 게이트 강제는 그렇지 않다.

### F-10 을 버리지 않는다

분리는 무시가 아니다. 지적 자체는 타당하다 — 호출자 없는 검사 스크립트는 검사하지 않는 것과 같다. 다만 **해소 방식이 아직 불충분**하므로 별도로 완결시킨다.
